# Development

## Make Targets

The `Makefile` is generated by [bmk](https://pypi.org/project/bmk/) (its first line reads
`# BMK MAKEFILE <version>`) and is rewritten when bmk updates it, so this file keeps no copy of the
target list. Run

```bash
make help
```

for the authoritative, current list: it reads the target comments from the Makefile itself.
`bmk --help` and `bmk <command> --help` describe the underlying commands.

The targets used day to day:

- `make dev` -- editable install with the dev extras (`uv pip install -e ".[dev]"`).
- `make test` -- the full local gate: ruff format and lint, bandit, import-linter, pip-audit,
  pyright and pytest with coverage (doctests included through `--doctest-modules`). It also
  raises dependency floors and applies ruff's formatting and fixes, so expect the working tree to
  change.
- `make testintegration` (aliases `testi`, `ti`) -- the integration tests only (SMTP, SSH
  connectivity, external resources).
- `make bump-patch` / `bump-minor` / `bump-major` -- bump the version in `pyproject.toml`, turn
  the `[Unreleased]` section of `CHANGELOG.md` into the new version, and rewrite
  `src/proxmox_srvbackup/__init__conf__.py` to match.
- `make push` -- run the tests, commit and push. Give the commit message with `MSG="..."` (it
  reaches bmk as `BMK_COMMIT_MESSAGE` and survives punctuation, newlines and `$`); without one,
  bmk prompts.
- `make release` -- tag the current version and create the GitHub release.

## Test Markers

| Command                | What it runs                                                       |
|------------------------|--------------------------------------------------------------------|
| `make test`            | All tests EXCEPT those marked `integration`                        |
| `make testintegration` | ONLY tests marked `integration`                                    |
| CI                     | All tests EXCEPT those marked `local_only` (`-m "not local_only"`) |
| `pytest tests/`        | ALL tests (no marker filter)                                       |

A test that needs external resources (a real SMTP server, SSH connectivity, a database) carries both
`@pytest.mark.integration` (so `make test` skips it and `make testintegration` runs it) and
`@pytest.mark.local_only` (so CI skips it).

### Email Integration Tests

To run email tests that actually send messages:

1. **Create a `.env` file** in the project root with your SMTP settings:

```bash
# .env (copy from .env.example)
EMAIL__SMTP_HOSTS=["smtp.example.com:587"]
EMAIL__FROM_ADDRESS=sender@example.com
EMAIL__RECIPIENTS=["recipient@example.com"]
EMAIL__SMTP_USERNAME=your_username
EMAIL__SMTP_PASSWORD=your_password
```

   Alternatively, use `--env-file` to point at an existing `.env` file:

```bash
proxmox-srvbackup --env-file /path/to/my/.env send-notification --subject "Test" --message "Hello"
```

2. **Run the integration tests**:

```bash
make testintegration
```

3. **Or run the email tests directly**:

```bash
pytest tests/test_mail.py -m integration -v
```

### Adding New Integration Tests

Mark tests that require external resources:

```python
@pytest.mark.local_only
@pytest.mark.integration
@pytest.mark.os_agnostic
def test_real_external_service(...):
    """Integration test requiring external service."""
    ...
```

These tests are skipped by `make test` and in CI, and run with `make testintegration`.

### SMTP Test Seam

`send_email()` and `send_notification()` accept an optional `transport` argument, forwarded
to `btx_lib_mail`'s `Transport` port. Unit tests inject a double (`RecordingTransport` in
`tests/test_mail.py`) rather than patching `smtplib.SMTP`, and assert on delivery intent:
envelope sender, recipients, host failover order, credentials, and the composed payload.

Do not go back to monkeypatching `smtplib`. btx_lib_mail streams the message over the wire
protocol itself (MAIL/RCPT plus DATA or BDAT), so a `MagicMock` does not honour the contract
and breaks whenever the library changes delivery strategy.

The `SendEmail` / `SendNotification` ports in `application/ports.py` deliberately omit
`transport`: a delivery mechanism is an adapter concern, not something the application layer
should see. The adapter still satisfies the Protocol because an extra keyword parameter with
a default is structurally compatible. Do not add `transport` to the port.

## Versioning & Metadata

- Single source of truth for package metadata is `pyproject.toml` (`[project]`).
- The package reads its own metadata from static constants in
  `src/proxmox_srvbackup/__init__conf__.py`; a version bump rewrites that file, so do not
  edit the version there by hand.
- The console script name is the static `shell_command` constant in `__init__conf__.py`
  (`proxmox-srvbackup`); `[project.scripts]` in `pyproject.toml` registers it together
  with `proxmox_srvbackup`.

## Dependency Auditing

- `make test` runs `pip-audit` against the project environment. If it reports a vulnerability,
  raise the affected floor in `pyproject.toml` (a transitive dependency goes into the dev extras
  with a comment naming the CVE).

## CI & Publishing

The GitHub Actions workflows under `.github/workflows/` are distributed from the
`default_cicd_public` template; change them there, not in this repository.

- `default_cicd_public.yml` -- lint, type-check and test on Linux, macOS and Windows for every
  Python version listed in the `pyproject.toml` classifiers, verify the pipx and uv installs and
  run the notebooks.
- `default_release_public.yml` -- on a `v*` tag, builds the artifacts and publishes them to
  PyPI, with the `PYPI_API_TOKEN` secret when it is set and otherwise through a PyPI Trusted
  Publisher (OIDC).

To publish a release:

1. `make bump-patch` (or `bump-minor` / `bump-major`), then commit and push.
2. `make release` tags the current version and creates the GitHub release; the tag starts
   `default_release_public.yml`.

## Codecov

- `make test` writes `coverage.xml`; `make codecov` uploads it.
- For private repos, set `CODECOV_TOKEN` (see `.env.example`) or export it in your shell.
- For public repos, a token is typically not required.
